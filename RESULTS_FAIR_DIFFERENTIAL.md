# Fair differential and status-vs-effect: results

**Outcome: both pre-registered hypotheses are supported.**

- **H1.** With two identities and their own authorization checks, every baseline found fewer
  of the 4 planted flaws than authz-fuzzer (4/4). The strongest, RESTler and Schemathesis,
  reached 2/4 each.
- **H2.** On the 4 status-vs-effect rows, authz-fuzzer got 4/4 right at its Verified tier.
  RESTler, the status-code oracle, got 0/4.

This replaces the earlier "each baseline 0/4" claim. That claim came from a single-identity
setup with the baselines' authz checks switched off.

- Pre-registration: `worklogs/09-fair-differential-prereg.md`, commit `cbab79d`, made before any
  run.
- Environment: `reports/fair-differential/ENV.md`.
- Raw output per tool and mode: `reports/fair-differential/<tool>/<mode>/` (raw tool output, exact
  command and exit code in `run.json`, normalized `findings.json`).
- Tables: `reports/fair-differential/report.md`, `status-vs-effect.md` and `scores.json`, all
  generated by `python3 lab/fair_differential.py report` from those files.
- Target: the Rust `authz-target` (branch `fair-differential` in `authz-fuzzer`), bound to
  127.0.0.1. No other host was contacted.

## Setup in one paragraph

Every tool got the same two identities: `alpha-admin` (owner) and `bravo-admin` (other tenant),
or `alpha-viewer` and `alpha-admin` for `admin-legit`. Each baseline ran its own authorization
checks:

- **RESTler:** source build with `namespacerule`, `useafterfree`, `resourcehierarchy`,
  `leakagerule` and `invaliddynamicobject`. Namespace `trigger_objects` and the fuzzing
  dictionary were seeded with the order ids. `fuzz --time_budget 0.05`.
- **EvoMaster 6.2.0:** black-box, with its post-search security / access-control phase. `--maxTime
  120s --seed 42`.
- **Schemathesis 4.32.0:** `--checks all`, which includes `object_level_authorization` and
  `ignored_auth`, with both users as peers. `--seed 42`.
- **authz-fuzzer:** its normal manifest-driven scan.

The target's OpenAPI document now declares response schemas. That lets every tool link
`POST /orders` to `/orders/{id}`, and lifted RESTler from 0/4 to **4/4 rendered-valid
operations** in every mode (`restler/*/testing_summary.json`).

## Task 3: recall over the 4 planted flaws (H1)

A flaw counts as detected only if the tool reports a finding of the relevant class on the flaw's
operations, and the same tool's run on the hardened server lacks that finding (pre-registered).

| Tool | xtenant-read | xtenant-write | missing-auth | shared-write | **Recall** | False findings on trap runs |
|---|---|---|---|---|---|---|
| authz-fuzzer | detected | detected | detected | detected | **4/4** | **0** (`none`, `delegated-read`, `public-read`, `admin-legit`) |
| RESTler | detected | detected | missed | missed | **2/4** | 3 (`none`, `admin-legit`) |
| Schemathesis | detected | missed | detected | missed | **2/4** | 3 (`none`, `admin-legit`) |
| EvoMaster | missed | missed | missed | missed | **0/4** | 0 |
| EvoMaster, security budget raised (sensitivity) | missed | missed | missed | missed | **0/4** | 0 |

What the baselines found:

- **RESTler's NamespaceRule** caught the cross-tenant read and write, by replaying the owner's
  requests with the attacker's token and seeing 2xx. It has no unauthenticated-access check, so
  its GET hit in `missing-auth` is the wrong class and is not credited. It never reached the
  shared order with a write. Its false findings are a `POST /orders` bucket in every run,
  including the hardened one: the attacker may legitimately create orders, but got 201 on a request
  that matched a trigger id. The third is the admin's policy-allowed GET in `admin-legit`.
- **RESTler never attempted to reproduce any of its 16 NamespaceRule buckets** ("Attempted to
  reproduce 0 time(s)"). The credited detections rest on single, unreplayed observations.
- **Schemathesis** caught the cross-tenant read with `object_level_authorization` (ST402) and the
  missing authentication with `ignored_auth` ("API accepts requests without authentication").
  Its object-level check replays **reads only**, so it cannot see cross-tenant or shared writes.
  Its false findings are an `ignored_auth` failure on `DELETE` in every run, and the admin's
  allowed read in `admin-legit`.
- **EvoMaster** used both identities (both tokens appear in its generated tests), but it emitted
  only XSS (301) and HTTP-semantics faults (109, 119). It reported no access-control category in
  any of 18 runs.

## Task 4: status vs effect (H2)

| Row | Correct verdict | authz-fuzzer | RESTler | Schemathesis | EvoMaster | EvoMaster (sensitivity) |
|---|---|---|---|---|---|---|
| `silent-write` (403, but applied) | verified violation | ✅ flagged (Verified, PATCH + DELETE) | ❌ missed | ❌ missed | ❌ missed | ❌ missed |
| `lying-success` (200, nothing applied) | no write violation | ✅ not flagged at Verified | ❌ flagged PATCH + DELETE | ✅* | ✅* | ✅* |
| `admin-legit` (allowed admin write) | no finding | ✅ not flagged | ❌ flagged GET | ❌ flagged GET | ✅ | ✅ |
| `leaky-404` (404 body = owner's order) | information disclosure | ✅ flagged (Verified `information_disclosure`) | ❌ missed | ❌ missed | ❌ missed | ❌ missed |
| **Rows correct** | | **4/4** | **0/4** | **1/4** | **2/4** | **2/4** |

\* Correct only in outcome. Schemathesis's object-level check does not replay writes, and EvoMaster
reported no cross-identity write fault in any mode, so neither judged these writes at all.
RESTler did test them, and its verdicts track the attacker's status code: it missed the write
that returned 403 but took effect, and flagged the one that returned 200 but changed nothing.

**authz-fuzzer's Probable tier, as pre-registered.** For `lying-success` the scanner emits a
*Probable* cross-tenant write finding on PATCH and DELETE. That is its documented rule for "2xx
but no owner-visible change; needs follow-up" (`authz-oracle/src/write.rs`). At the Verified
tier, which is its CI gate and the primary scoring, the row is correct. Counting Probable
findings, it would score 3/4. Both are reported.

## Deviations from the pre-registration (all disclosed)

1. **Order of work.** The pre-registration was written after installing the tools and reading
   their docs, `--help` and source, so it could name real switches. No tool had touched the target
   by then.
2. **Development runs.** One Schemathesis, two EvoMaster and two RESTler runs against the hardened
   `none` mode were used to learn each tool's output format. They ran in a scratch folder, were not
   committed, and are not scored. Every scored run was a fresh run by the committed driver.
3. **RESTler checker syntax.** The prompt's `--enable_checkers NamespaceRule UseAfterFree …` is
   rejected by this build ("Unknown checker NamespaceRule"; "Invalid argument: UseAfterFree").
   The same five checkers were passed as `namespacerule,useafterfree,resourcehierarchy,leakagerule,invaliddynamicobject`.
4. **RESTler engine Python.** The first scored RESTler pass used Python 3.15. RESTler picked
   `python3` and ignored the `python` shim. It was stopped after its `none` run, which had the same
   `POST /orders` bucket. All 9 modes were rerun with `--python_path` pinned to Python 3.12.15,
   three runs at a time.
5. **RESTler wall time.** Despite `--time_budget 0.05` (3 min), runs took 8–53 min
   (`run.json: wall_s`). RESTler appears to check the budget only between generations.
6. **EvoMaster rate cap.** The first EvoMaster development run crashed with `BindException: Can't
   assign requested address`, after exhausting all 16,384 ephemeral ports. Scored runs used
   `--ratePerMinute 1800`, and the driver waits for the TIME_WAIT backlog to drain.
7. **EvoMaster sensitivity run (added after seeing results).** In every pre-registered run, the
   security phase hit its limit ("Phase 'SECURITY' has timed out after 12 seconds"). Because a
   time-out is not a fair test, all 9 modes were rerun with `--extraPhaseBudgetPercentage 1.0`.
   The phase then completed in 15–16 s, still with no access-control fault. The pre-registered run
   stays primary. The sensitivity run can only have helped the baseline, and it changed nothing.
8. **Target spec.** The OpenAPI response schemas were added for every tool alike, as
   pre-registered. The earlier differential injected a dummy `responses` block for RESTler only.

## Limits

- **One run per tool per mode.** Fixed seeds were used where available (EvoMaster 42,
  Schemathesis 42, RESTler's default 12345). Fuzzers are stochastic, and another run could find
  more or less. No confidence interval is claimed for k/4 over 4 flaws.
- **Synthetic target.** The target is small, built by the scanner's author, and its flaws and
  traps were written to exercise authz-fuzzer's oracle paths. This shows the design claim on
  that target; it does not measure performance on real APIs.
- **Same-author risk.** The scoring rules were fixed before the runs, but one person wrote the
  target, the candidate and the scoring. Independent review is still needed.
- **Burp Autorize** was not run (commercial GUI). EvoMaster white-box does not apply to a Rust
  binary.

## SOP:

- SOP: On writes engineered to separate response from effect, Lattivant classified 4/4 correctly where RESTler misclassified 4/4, Schemathesis 3/4 and EvoMaster 2/4.
- SOP: With multi-identity configuration and authorization checkers enabled, authz-fuzzer detected 4/4 planted authorization flaws vs 2/4 for the strongest baselines (RESTler and Schemathesis), with 0 false findings on trap modes vs 3 each.
- SOP: The status-code oracle failed in both directions: RESTler missed a cross-tenant write that returned 403 but took effect, and flagged one that returned 200 but changed nothing.
